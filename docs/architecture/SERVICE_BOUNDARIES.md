# Service boundaries

All services have separate deployable artifacts, credentials, persistence and OpenAPI contracts. Events are versioned facts. Dependencies point to contracts, never another service's database. Each domain validates authorization for its own operations.

| Service | Responsibilities and owned data | Public API and events | Dependencies, security and scaling |
|---|---|---|---|
| API Gateway | Public routing, TLS termination integration, request IDs, API versioning, coarse rate limits and token checks; no business database | Versioned `/api/v1` routes; emits access telemetry, not domain facts | Calls service APIs; protect against abuse, strip spoofed identity headers. Stateless; scale on request volume. |
| Identity & Access | Registration/login/logout, password recovery, email/phone verification, credentials, refresh sessions, roles/permissions | Auth REST; `UserRegistered`, `ContactVerified`, `RoleGranted`, `SessionRevoked` | Own identity DB; password hashing (Argon2id or equivalent reviewed parameters), rate limits, MFA-ready admin policy, hashed rotating refresh tokens. Scale auth bursts independently. |
| Student Verification & Seller | Student profile/eligibility case, seller applications, manual review, rejection/resubmission history, storefront profile and approval state | Student/seller REST and admin review API; `VerificationSubmitted`, `SellerApproved`, `SellerRejected`, `StorefrontChanged` | Own seller DB; tightly restrict student evidence, reviewer authorization, audit every decision. Scale review/API workload. |
| Marketplace & Catalogue | Categories, products, variants, images metadata, searchable listing, availability projection, storefront discovery | Catalogue/storefront REST; `ProductPublished`, `ProductChanged`, `ProductArchived` | Own catalogue DB; validate seller status using event projection; image bytes belong in object storage later. Scale read/search independently; add search engine only when justified. |
| Inventory | On-hand/reserved quantities, movements, reservations, reconciliation and low-stock signals | Stock/reservation REST for synchronous checkout; `StockReserved`, `StockReservationExpired`, `StockAdjusted`, `LowStock` | Own inventory DB; optimistic concurrency/constraints, idempotent reservation IDs. Scale write throughput and consumers independently. |
| Order & Commerce | Cart, checkout orchestration, customer order and seller suborders, status history, cancellation workflow, saga state | Cart/order/checkout REST; `OrderPlaced`, `OrderCancelled`, `OrderPaid`, `OrderFulfilmentRequested` | Own commerce DB; customer/seller scoped access, idempotency, saga compensations. Calls inventory/payment synchronously for immediate decisions; scales checkout separately. |
| Payment | Provider-neutral payment intents, provider adapters, transaction ledger, webhook validation, reconciliation/refund operations | Payment intent/status/refund REST; `PaymentPending`, `PaymentSucceeded`, `PaymentFailed`, `RefundUpdated` | Own payment DB; secrets from secret manager, signature/auth validation, replay protection, never trust browser redirects. Scale callbacks and reconciliation workers separately. |
| Fulfilment & Delivery | Seller-arranged delivery, campus pickup, partner details, delivery instructions/status, external tracking reference/URL | Fulfilment REST; `FulfilmentCreated`, `FulfilmentStatusChanged`, `FulfilmentDelivered` | Own fulfilment DB; minimize customer contact data, seller/partner scoped access. No proprietary live GPS in foundation. Scale updates independently. |
| Notifications | Email and in-app messages, templates, preferences, delivery attempts; SMS behind justified provider adapter | Preference/inbox REST; consumes domain events and emits `NotificationDeliveryFailed` telemetry/event | Own notification DB; redact sensitive content, unsubscribe/preferences, provider credentials isolated. Scale consumers by queue depth. |
| Administration & Analytics | Moderation console APIs, platform-wide audit index, operational reporting projections | Admin REST; consumes domain events into projections; audit export | Own admin/projection DB. No cross-database queries. Strong admin authorization and immutable/auditable decisions. Reporting scales on projections, not OLTP stores. |

## Initial deployment shape

The architecture keeps all ten logical domains explicit. Initial NestJS deployables should include gateway, identity, seller, catalogue, inventory, commerce, payment, fulfilment and notification. Administration begins as a protected React/admin API capability using domain-owned admin endpoints and a projection worker; it becomes a distinct deployable when reporting/moderation ownership warrants it. This avoids forcing a separate low-volume analytics service before it has a distinct runtime need. Fulfilment remains a logical boundary and can initially share the Commerce release pipeline only if its data store and module boundary remain isolated; prefer separate deployment once lifecycle and operators emerge.

Stage 4 created nine NestJS apps: API Gateway plus the eight deployables listed above. Administration & Analytics remains a logical boundary without a standalone NestJS app, as approved in the planning documents. The gateway currently exposes versioned health/OpenAPI scaffolding; routing, identity enforcement and gateway rate limiting are not yet implemented.

## Data and event ownership

Only the owner changes a domain fact. Events describe committed changes and contain IDs/minimal data, never secrets or full student documents. Consumers maintain projections and deduplication records in their own stores. A service publishes its outbox after local commit; retries may cause duplicate delivery, so every consumer is idempotent.
